3. Project Overview

CampusRide is an institutional, peer-to-peer carpooling, bike-pooling, and micro-mobility network engineered exclusively for university ecosystems. Designed to solve commuter bottlenecks between campus gates and surrounding student residential hubs (e.g., Premnagar, Selaqui, Suddhowala, Vikasnagar in the Dehradun educational cluster), CampusRide enables verified students and university faculty to share daily commutes safely, legally, and at transparent, non-profit cost-sharing rates.

Key Differentiators

  • Closed Institutional Trust Ring: Strictly restricted to verified university students with official .edu emails, physical student ID OCR verification, and facial biometrics.
  • Academic Affinity Engine: Passengers are prioritized with drivers from their exact course, semester, and department (e.g., B.Tech CSE Classmates).
  • Zero-Commission Fair-Share UPI: Drivers receive 100% of fuel-share contributions directly via native upi://pay deep-links without platform cuts or third-party escrow fees.
  • Dual-Layer Pickup Verification: Cryptographically generated CSPRNG 6-digit OTPs and QR codes ensure physical presence verification before trips commence.

4. Problem Statement

University campuses across India face severe transit and safety deficiencies that impact thousands of students twice daily:

Domain Existing Manual / Commercial Reality CampusRide Solution
Safety & Trust Unregulated WhatsApp / Telegram carpool groups with total anonymity; no vetting of external strangers entering campus vehicles. Mandatory university ID verification, face biometrics, emergency contact dispatch, and in-app SOS with live GPS link.
Transit Bottlenecks Auto-rickshaws overcharge students (₹80–₹120 for 3 km) during peak 8:30 AM and 4:30 PM university gate rushes. Pre-scheduled peer carpools at capped fuel-split rates (₹20–₹35) between residential hubs and campus gates.
Identity Fraud Students use fake names and temporary phone numbers on social messaging channels. Argon2id credential security, institutional email token verification, and automated ID card OCR.
Coordination Chaos Chat groups get flooded with spam, lost pickup messages, and unconfirmed ride promises. Structured ride state machines, seat capacity locks, and dedicated room-scoped coordination chat.

6. Core Features

CampusRide encapsulates 24 mission-critical feature modules spanning student commuters, drivers, and campus safety officers:

  • Student & Driver Registration: Multi-step registration capturing academic identity (college, branch, department, semester, year).
  • Institutional Email Verification: Single-use cryptographic tokens dispatched via email (Resend API) ensuring .edu authenticity.
  • Phone & WhatsApp Verification: Direct OTP delivery through integrated WhatsApp service (Baileys engine).
  • Student ID Card OCR & Biometric Upload: Secure multi-file document upload handling student IDs and face photos with automatic data extraction.
  • Daily Driver ID & Facial Check: Liveness and verification challenge prior to daily ride dispatch.
  • Road-Aware Ride Offer Creation: Driver sets origin, destination, departure time, available seats (1–6), and route summary with interactive Leaflet map dragging.
  • Recurring Weekly Commutes: Toggle automated Monday–Friday schedules matching semester timetables.
  • Campus Landmark Quick-Picks: One-tap selection of recognized gates (UIT Gate 1, Hostel Block A/B, Central Library Roundabout, Premnagar Chowk).
  • Intelligent Corridor Search: Passengers search routes with distance bounding, detour minutes, and time tolerance windows.
  • Academic Affinity Engine: Algorithmic matching calculating classmate bonuses and department prioritization.
  • Guarded Seat Requests: Atomic seat decrement preventing concurrency race conditions.
  • Real-Time Coordination Chat: In-app chat modal with instant quick-chips ("I've arrived at Gate 1", "Running 2 mins late").
  • CSPRNG OTP & QR Pickup Verification: 6-digit cryptographic OTP displayed exclusively to the driver; scanned/entered by passenger to begin trip.
  • Live Telemetry & Route Tracking: Smooth vehicle icon translation along the corridor via WebSockets.
  • Zero-Commission UPI Payment Deep Links: Passenger taps "Pay ₹30 via GPay / PhonePe / Paytm" launching upi://pay with driver's UPI ID.
  • Mutual Peer Reviews & Ratings: Two-way reviews updating composite driver reliability and passenger scores.
  • Idempotent SOS & WhatsApp Emergency Dispatch: Panic button triggers instant WhatsApp alert with Google Maps coordinate link to family contacts.
  • Institutional Admin Command Center: Real-time review queue, telemetry counters, safety incident logs, and university verification approvals.
  • CO₂ & Fuel Savings Impact Dashboard: Cumulative environmental sustainability metrics.
  • Installable PWA: Standalone web manifest and hardened Service Worker for Android/iOS home screen installation.

PART 4 — FRONTEND ARCHITECTURE

11. Frontend Architecture

The client application is built with React 19, TypeScript, and Vite, packaged as an installable Progressive Web App. State is managed via lightweight React Context providers (AuthContext, RideContext, ThemeContext) to eliminate Redux boilerplate while maintaining immediate reactive state across routes.

  • Client API Layer (client/src/services/api.ts): Centralized HTTP client managing JWT authorization bearer tokens, error code normalization, and automatic retries.
  • Real-Time WebSocket Client (client/src/services/socket.ts): Singleton Socket.IO instance establishing authenticated socket handshakes and room subscriptions.
  • Responsive Layout Hierarchy: Modular page shells featuring persistent mobile navigation bars, desktop header links, and translucent glassmorphism background components.

PART 7 — CORE ENGINEERING LOGIC

21. Ride Creation Logic

  1. Driver Authentication & Approval Gate: Verifies active JWT token and validates that isVerificationApproved(user) returns true. Unverified drivers receive 403 Forbidden.
  2. Vehicle Linkage: Queries Vehicle collection for driver's registered car or bike. If missing, dynamically provisions a verified vehicle record from submitted payload.
  3. Geospatial Sanitization: Validates origin and destination coordinates are within latitude [-90, 90] and longitude [-180, 180].
  4. Road Polyline Ingestion: Connects to OSRM engine to capture real turn-by-turn road geometry, road distance in meters, and estimated transit duration in seconds.
  5. Fair-Share Fuel Cap: Enforces minimum price (₹10) and checks price per seat against campus fuel-share standards (preventing commercial gouging).
  6. Recurring Weekly Scheduling: If recurring: true, generates timetable matrix matching selected days of the week (e.g. Mon–Fri at 8:30 AM).

22. Ride Search Logic

  1. Coordinate Extraction: Accepts passenger pickup (originLat, originLng) and optional destination coordinates.
  2. Active Candidate Filtering: Queries Ride collection for status: 'active' and availableSeats >= requestedSeats with departure times >= current time.
  3. Corridor Bounding: Calculates passenger proximity to driver's route polyline. Pickup must fall within acceptable walking tolerance (default 1.5 km).
  4. Directional Alignment Check: Evaluates vector cosine similarity between passenger journey and driver route to ensure trips travel in the same physical direction.
  5. Scoring & Priority Sorting: Computes comprehensive match score (0–100%) and sorts results by academic affinity rank, match score, and departure time.

23. Matching Engine Architecture

The matching engine evaluates 10 multidimensional criteria across geographical, temporal, academic, and behavioral vectors:

  • Route Corridor Distance: Measures perpendicular distance from passenger pickup to driver's road trajectory.
  • Directional Vector Alignment: Disqualifies reverse commutes (e.g., driver heading toward campus vs passenger heading away).
  • Time Gap Clamping: Penalizes departures diverging from passenger requested time. Time difference > 15 mins clamps to 0 time match score.
  • Detour Penalty: Computes additional kilometers the driver must divert to pick up the passenger.
  • Academic Affinity Tiering: Awards major priority multipliers for shared courses, departments, and semesters.
  • Driver Reliability Score: Factors driver punctuality, completed rides, and peer rating (1.0–5.0 scale).
  • Gender Preference Hard Gates: Strictly eliminates male drivers when a female passenger selects women-only carpools.

24. Mathematical Matching Score Formula

MatchScore = (W_geo × S_geo) + (W_time × S_time) + (W_academic × S_academic) + (W_rating × S_rating) - DetourPenalty Where: - W_geo = 0.40 (Geographic Corridor Proximity) S_geo = max(0, 1 - (PickupDistanceKm / MaxCorridorRadiusKm)) - W_time = 0.25 (Temporal Synchronization) S_time = max(0, 1 - (|DepartureTime - TargetTime| in minutes / MaxWaitMinutes)) - W_academic = 0.25 (Institutional Affinity Tier) S_academic: * 1.00 = Classmate (Exact Same Course & Semester, e.g. B.Tech CSE Sem 6) * 0.75 = Department Peer (Same Department, Different Semester) * 0.50 = Campus Peer (Same University, Different Department) * 0.00 = Different Institution - W_rating = 0.10 (Driver Reliability) S_rating = (DriverRating - 1.0) / 4.0

[DRAFT] ──> Driver inputs route & seats │ ▼ [PUBLISHED] ──> Active on Search Feed (availableSeats > 0) │ ├──> [FULL] (availableSeats == 0, waitlisted) │ ▼ [IN_PROGRESS] ──> Driver initiates trip; OTP issued │ ├──> [COMPLETED] ──> All passengers dropped; ratings unlocked │ └──> [CANCELLED] ──> Driver cancels prior to start; seats released

26. Request State Machine & Race-Condition Prevention

[PENDING] ──> Passenger requests seat (atomic compound index guard) │ ├──> [DECLINED] ──> Driver rejects; no seats deducted │ ├──> [CANCELLED] ──> Passenger cancels before acceptance │ ▼ [ACCEPTED] ──> Atomically decrements availableSeats ($gte: 1, $inc: -1) │ Adds passenger to real-time chat group │ ├──> [CANCELLED_AFTER_ACCEPT] ──> Atomically restores seat ($inc: +1) │ ▼ [TRIP_STARTED] ──> Included in trip passengerIds │ ▼ [COMPLETED] ──> Reached destination; prompts UPI deep link & review

27. Trip Lifecycle Walkthrough

  1. Ride Scheduled: Passengers booked; countdown timer active.
  2. Driver Departure: Driver taps "Start Commute". Server transitions trip state to in_progress.
  3. Cryptographic OTP Dispatch: Server generates 6-digit random CSPRNG OTP, salted and hashed into MongoDB. Plaintext OTP sent strictly to Driver.
  4. Physical Pickup: Passenger enters Driver's car, asks for OTP or scans QR. Passenger submits OTP to /api/trips/:id/verify-otp.
  5. Constant-Time Verification: Server executes timing-safe check. On match, emits tripUpdate via Socket.IO.
  6. En-Route Telemetry: Vehicle location streamed every 5 seconds.
  7. Trip Completion: Driver taps "Finish Trip". Ride marked completed; driver total rides incremented; review modals trigger on passenger screens.

PART 12 — SECURITY SPECIFICATION

46. Security Architecture & Defense-in-Depth

  • Content Security Policy (CSP): Explicit helmet directives restricting script execution to self and authorized CDN fonts.
  • Cross-Site Request Forgery (CSRF): Bearer-based JWT tokens stored in browser local storage, completely immune to traditional cookie CSRF attacks.
  • Broken Object Level Authorization (BOLA): Strict ownership middleware ensuring users can only modify their own rides or cancel their own requests.
  • Parameter Pollution Prevention: Express hpp middleware blocks duplicate query string attacks.
  • Brute-Force Rate Limiting: Tiered IP rate limiting (100 reqs/15 mins on general endpoints; 5 reqs/15 mins on login/OTP endpoints).

47. Threat Model & Mitigation Matrix

Threat Vector Potential Attack Method Platform Defense Automated Test Verification
JWT Signature Tampering Attacker alters token payload to claim campus_admin role. Strict HMAC SHA-256 signature check with secret verification. PASS: Tampered token signature is rejected with 401
BOLA Ride Hijacking User B attempts to delete or modify User A's ride offer. Resource creator ID comparison against authenticated JWT user ID. PASS: User B cannot cancel or delete User A's ride offer
Seat Oversell Race 10 passengers click "Book Last Seat" concurrently at exact same millisecond. Guarded atomic MongoDB update: { availableSeats: { $gte: 1 } }, { $inc: { availableSeats: -1 } }. PASS: Concurrent accept requests cannot oversell seats
OTP Brute Force Passenger attempts to guess 6-digit OTP through repeated script requests. Lockout counter triggers trip.isLocked = true after 5 failed attempts; 15 min expiry. PASS: 5 incorrect OTP attempts lock out the trip
Third-Party OTP Bypass Unauthorized user attempts to verify OTP on a trip they are not part of. Strict participant membership validation. PASS: Unrelated third party cannot verify pickup OTP

PART 19 — BUGS & ENGINEERING HISTORY

73. Critical Bugs Fixed & Root Cause Analyses

Bug 73.1: Module Script Strict MIME Type Checking Failure

Problem Statement
Browser console halted with error: "Failed to load module script: Expected a JavaScript-or-Wasm module script but the server responded with a MIME type of 'text/html'. Strict MIME type checking is enforced for module scripts per HTML spec."
  • Root Cause: The PWA Service Worker (sw.js) was unconditionally registered during local Vite development. When Vite rebuilt dependencies or changed internal chunk hashes, the active service worker intercepted chunk requests and returned cached index.html (MIME text/html). Additionally, vercel.json wildcard rewrites redirected missing .js files to index.html.
  • Engineering Fix: (1) Configured client/src/main.tsx to register SW strictly in production (import.meta.env.PROD), and in development aggressively unregister existing workers and clear caches. (2) Hardened sw.js to bypass all Vite paths (/@, /src/, /node_modules/) and restrict HTML fallback to event.request.mode === 'navigate'. (3) Updated vercel.json and Express static routing to return HTTP 404 for missing code files instead of HTML.
  • Files Modified: client/src/main.tsx, client/public/sw.js, client/vercel.json, client/vite.config.ts, server/src/app.ts.
  • Commit Hash: c38fa18.
  • Status: Verified & Resolved.

Bug 73.2: Admin Verification Queue Desync for New Accounts

Problem Statement
Newly registered accounts (such as RaistarPhp) with pending/unverified status were not surfacing in the Institutional Admin Review queue.
  • Root Cause: The Admin Review endpoint queried only the VerificationRequest collection. Accounts created through registration or OAuth had updated their User.verificationStatus, but had not yet created a separate VerificationRequest document.
  • Engineering Fix: Introduced an Auto-Sync Engine in server/src/routes/verificationRoutes.ts and client/api/index.ts that automatically queries all accounts with verificationStatus: { $in: ['pending', 'unverified'] } and injects them dynamically into the admin queue.
  • Commit Hash: 947dcdd.
  • Status: Verified & Resolved.

Bug 73.3: Multer Document Upload Field Name Mismatches

Problem Statement
Document upload failed with Unexpected field error when students submitted ID cards.
  • Root Cause: Multer middleware was expecting idCardPhoto and licensePhoto, whereas frontend forms submitted idDocument and drivingLicense.
  • Engineering Fix: Added dual-field Multer mappings accepting both naming conventions seamlessly.
  • Commit Hash: 947dcdd.
  • Status: Verified & Resolved.

Bug 73.4: Concurrent Seat Oversell Race Condition

Problem Statement
Simultaneous seat acceptances on the final available seat could cause availableSeats to drop to negative values.
  • Root Cause: Non-atomic read-then-write logic in route controllers.
  • Engineering Fix: Implemented guarded atomic MongoDB update: { _id: rideId, availableSeats: { $gte: 1 } }, { $inc: { availableSeats: -1 } }. If another request claims the seat first, the second update returns null and triggers 409 SEATS_UNAVAILABLE.
  • Status: Covered by automated test in tests/securityPatch.test.ts.

PART 20 — KNOWN LIMITATIONS

74. Explicit Platform Limitations

In accordance with rigorous engineering honesty, the following real-world limitations are acknowledged:

  • UPI Confirmation is User-Mediated: CampusRide generates native upi://pay deep links for zero-commission peer payments. Because there is no paid centralized payment gateway (Razorpay/Stripe), payment confirmation is acknowledged directly by the driver rather than verified via webhook callback.
  • Client-Side ID OCR Accuracy: Client-side optical character recognition performance is dependent on student camera resolution, lighting, and ID card wear. Degraded images require manual admin visual review.
  • GPS Precision in Dense Foothills: In mountain-adjacent campuses (e.g. Dehradun foothills), mobile GPS accuracy may drift by 15–30 meters under cloud cover or tree canopies.
  • Public OSRM Rate Availability: When utilizing public OSRM demo endpoints, routing requests may experience latency during high global loads. Production clusters require a self-hosted OSRM container.
  • WhatsApp Headless Session Heartbeats: The Baileys WhatsApp integration requires active WhatsApp Web QR authentication. If the paired campus phone loses internet or re-authenticates, alerts fall back to in-app and email channels.
