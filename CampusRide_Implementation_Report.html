1. Executive Summary & Problem Context

CampusRide is an enterprise-grade university carpooling and student mobility network built to address the critical transport bottleneck experienced daily by university students across Dehradun, Uttarakhand (Uttaranchal University, UPES, Graphic Era).

Prior to CampusRide, students relied on informal WhatsApp groups with unverified strangers, unsafe vehicle overloading, predatory auto-rickshaw fares, and zero digital safety oversight. CampusRide solves this with a verified academic trust framework: strict institutional email and ID card validation, real-time road corridor matching, daily driver liveness checks, and instant WhatsApp emergency dispatch.

3. High-Impact Daily Commute Upgrades

To eliminate friction from repetitive manual actions and ensure high student driver retention, the following daily commute features were designed and deployed:

  • Recurring Weekday Commutes (Mon–Fri Schedules): Drivers can toggle a semester-long recurring schedule. The ride engine automatically surfaces the ride for regular morning slots (e.g. 08:30 AM), eliminating the need to post manually every day. Handled through embedded Mongoose schema subdocuments (daysOfWeek: [1,2,3,4,5], time: string).
  • Zero-Commission Direct UPI Fare Settlement: Drivers store their UPI VPA (e.g., driver@okhdfcbank). When a trip finishes, passengers receive a direct settlement modal with standard upi://pay?pa=...&am=... deep links for Google Pay, PhonePe, and Paytm, accompanied by an instant copy-to-clipboard action. Zero payment gateway commissions are deducted.
  • Quick Commute Chat Presets: Pre-programmed one-tap coordination chips embedded in the in-ride coordination chat modal ("📍 I've arrived at pickup gate", "⏳ Running 3 mins late", "📚 Waiting by library steps") allow instantaneous communication without typing while walking or driving.
  • Campus Landmark Selection: Rapid one-tap selector pills for all major campus hubs: UIT Engineering Porch, USCS Computing Quad, Central Library, Premnagar Chowk Market, and Suddhowala PG hub.

4. Trust, Safety & Verification Architecture

Zero-Trust Academic Verification Gating:
Unverified or pending accounts are strictly barred on both frontend UI layers and backend server endpoints. Unverified students cannot create rides (403 FORBIDDEN) or send seat requests (VERIFICATION_REQUIRED).

A. Client-Side Student ID Card OCR Pre-Screening

An intelligent client-side OCR pre-screening parser was integrated directly into the verification submission workflow. When a student uploads their college ID card image, the system inspects the image buffer, automatically extracting student roll numbers, college names, and academic branches, pre-populating fields and accelerating administrative review.

B. Live WhatsApp Emergency SOS Integration

During an active trip, passengers and drivers have access to a one-tap SOS safety system. Triggering the emergency action automatically records an EmergencyIncident in MongoDB, idempotently prevents duplicated alarms, and dispatches a pre-formatted WhatsApp alert containing real-time Google Maps GPS coordinates directly to the user's designated emergency contacts.

C. Daily Physical Driver ID Check

Before starting the first trip of each day, drivers must complete a physical student ID verification step via DailyDriverIdCheckModal. This ensures the driver operating the vehicle matches the registered student credentials on file.

D. Verified Driver Badges & Academic Affinity

Ride cards now render visual trust badges so passengers can make informed decisions before requesting:

🎓 Classmate / Same Dept ⚡ Top Punctual Driver (10+ rides) 🌿 Eco Commuter (50+ kg CO₂ saved) 🔁 Mon–Fri Regular Commute

7. Critical Bug Fixes & Code Hardening

Component / Module Root Cause Surgical Resolution
Recurring Commute Mongoose Schema recurringSchedule was passed as a string or unstructured object, throwing Mongoose cast error ObjectExpectedError on ride creation. Added recurring: { type: Boolean, default: false } to RideSchema and sanitized recurringSchedule into structured { daysOfWeek: [1,2,3,4,5], time } in rideRoutes.ts.
False-Positive Driver Check-In for Passengers In RideDetailPage.tsx and TripTrackingPage.tsx, isDriver was computed as ride?.creator?._id === user?._id. On initial load, both were undefined, causing undefined === undefined to evaluate to true and flash driver actions to passengers. Hardened with safe ID extraction and boolean validation: Boolean(rideCreatorId && currentUserId && rideCreatorId === currentUserId).
Stale Request Cache on Unverified Users Search page read stale campusride_local_requests from localStorage during initial render state initialization, briefly showing "Request Sent" before verification sync. Added verification check in initial useState initializer: if user is not verified, returns an empty set immediately.
